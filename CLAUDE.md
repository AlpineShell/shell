# CLAUDE.md

This file provides context for AI assistants working on the alpine-shell codebase.

## Project Overview

Alpine Shell is a Windows desktop shell replacement built with Electron, React, TypeScript, and Tailwind CSS. It provides a topbar with system controls (volume, brightness, Wi-Fi, Bluetooth) and a desktop wallpaper layer. Windows only — uses Win32 APIs via koffi (FFI) and PowerShell for system integration.

## Repository Layout

This is a Bun-workspaces monorepo. Run all commands from the repo root.

- `apps/desktop/` — the Electron desktop shell (the original app; package name `alpine-shell`). Its build/release config (electron-builder, Railway/MinIO publish) lives in `apps/desktop/package.json`.
- `packages/plugin-sdk/` — `@alpine/plugin-sdk`, the contract plugins build against. Licensing has no shared package: the desktop verifies server-signed licence tokens in `apps/desktop/electron/licenceToken.js` against the keys baked into `electron/licenceConfig.generated.js`, and the account service ([AlpineShell/auth](https://github.com/AlpineShell/auth)) owns purchases, licences and activations.
- `apps/desktop/vendor/` — the vendored release tarball of `@alpine/ui` ([AlpineShell/ui](https://github.com/AlpineShell/ui)), the shared React primitives (Button, Row, Toggle, …) and design tokens that settings and setup render with. Import primitives by name from `@alpine/ui`. A missing prop or look goes into the library and ships as a release, never into a local copy; `bun run propagate` in the ui repo opens the bump PR here.

The website (marketing, docs, plugin marketplace pages) lives in its own repo: [AlpineShell/website](https://github.com/AlpineShell/website).

Unless noted otherwise, file paths in the sections below are relative to `apps/desktop/`.

## Architecture

### Two-Process Model (Electron)
- **Main process** (`electron/main.js`): Creates one desktop window and one topbar window per display. Manages display hotplug, appbar registration, and cursor tracking for the transparent topbar.
- **Renderer process** (`src/`): React app that renders in two modes based on URL param (`?mode=desktop` or `?mode=topbar`).

### Module System (Backend)
Each backend module in `electron/modules/` exports:
- `handlers`: Object mapping IPC channel names to handler functions (registered via `ipcMain.handle`)
- `start(broadcast)`: Function called once at startup to begin polling. `broadcast(channel, data)` sends to all renderer windows.

Modules are registered in `electron/main.js` via `ipc.register(...)`.

The preload asks the main process for boot data with `ipcRenderer.sendSync` before any page renders, and a sync message nobody answers blocks that renderer for good: the desktop stays its bare `#1a1a2e` and the Ridge never appears. Answer every sync channel with `ipc.answerSync(channel, read)`, which replies `null` when `read` throws, and register it first in `start`, before anything that can fail. A `start` that throws and a reply that fails are written to `<userData>/crash-log.json`.

### Hook Pattern (Frontend)
React hooks in `src/hooks/` follow a consistent pattern:
- Use `useShellState` for read-only state (fetch initial value, subscribe to changes)
- Hooks with setters (useVolume, useMonitors) add optimistic local state updates

### IPC Bridge
`electron/preload.js` exposes `window.shell` and `window.topbar` APIs via Electron's context bridge. Types are defined globally in `src/types/shell.d.ts`. `window.licence` and most of `window.setup` exist only on the page whose mode is `setup`; the `settings` page gets only the revert actions of `window.setup` (`revertTemporary`, `revertPermanent`, `uninstall`, and for a test-out `isTestSession` and `endTestSession`) and `restartShell`, which the search-only Restart Alpine Shell result calls. The `setup/*` and `licence/*` handlers are wrapped by `electron/trustedSenders.js`, and each group names the one window it answers, as `main.js` registered it: the licence and install channels answer only the setup window, the revert channels and `setup/restart-shell` only the settings window, and so do `plugins/set-enabled`, `plugins/marketplace-install` and `plugins/marketplace-uninstall`. Plugin widgets and plugin windows never see either bridge. Plugin settings pages and the Ridge page's live preview do import plugin renderer code into the settings window's main world, so that code can reach the revert actions (uninstall also releases the licence seat) and the plugin install, uninstall and enable channels: plugins are trusted code until their UI runs outside that realm.

Every invoke handler is also checked against the page that sent it: `ipc.register(...)` and `ipc.handle(channel, handler)` wrap each handler with `trustedSenders.guardShellSender`, which refuses a call unless the sender frame shows the shell's own page (the packaged `dist/index.html`, or the Vite dev server in development) or, for the `plugin-window/*` channels only, an `alpine-plugin://<id>/` page of the plugin the call names. The URL rules live in `electron/pageUrls.js`. Register new handlers through `ipc.register` or `ipc.handle`, never with `ipcMain.handle` directly. The same rules keep every window on its own pages: `electron/shellPageGuard.js`, which `main.js` attaches to every web contents, denies `window.open` (an https link opens in the browser instead) and blocks a navigation or redirect that leaves the shell page, or in a plugin window that plugin's own `alpine-plugin://<id>/` pages, and `main.js` grants no web permission other than `clipboard-sanitized-write`. A release build has no application menu and no DevTools, and the built page carries a Content-Security-Policy (`vite.config.ts`) that allows no inline, evaluated or remote script: never add an inline `<script>`, `eval` or `new Function`.

### Licence Module
`electron/modules/licence.js` owns the desktop side of licensing: it reads `<userData>/licence.json`, verifies the Ed25519 licence token offline against the public keys baked into `electron/licenceConfig.generated.js` (written by `scripts/generateLicenceConfig.js`; a release build reads only that file and ignores every environment variable), computes the state (`development`, `valid`, `unlicensed`) with the pure state machine in `electron/licenceState.js` and runs the device-flow sign-in against the auth service. A licence is activated once, online, at install, and the token carries no expiry: after activation the desktop never calls the account service for licensing again, so a PC that is offline forever keeps working forever. Nothing about the PC is collected after activation; at activation the installer sends the hashed device id, the app version, the Windows computer name as the display name the account page shows and a binding proof: a tier label (`tpm`, `dpapi` or `machine`) and one opaque base64url sha256 hash, which the server puts in the token as the `bind` claim. The proof is built by the pure ladder in `electron/licenceBinding.js` (tested on Linux CI with fake providers) over the providers wired in `electron/licenceBindingProviders.js`: first a non-exportable ECDSA P-256 key persisted in the Microsoft Platform Crypto Provider through CNG (`electron/platformCrypto.js`, koffi over `ncrypt.dll`; the hash is over the exported public blob and every check signs a fresh challenge that Node verifies), else a 32-byte secret sealed with `safeStorage` in `<userData>/licence-binding.json` (`electron/bindingSecretStore.js`; the hash is over the plaintext, which never leaves the machine and cannot be unsealed elsewhere), else sha256 over MachineGuid, the system volume serial and the SMBIOS UUID together (`electron/machineFingerprint.js`). The TPM public key, the sealed secret, the volume serial and the SMBIOS UUID are never sent: only the tier and the hash leave the machine. The binding hash is the anti-copy proof; the device id (sha256 of MachineGuid) is the convenience that lets the same PC re-activate after a reinstall without consuming a seat, and both stay. At every start the desktop reproduces the proof and compares it with the claim in constant time; a mismatch (a cleared TPM, a new motherboard, a rebuilt Windows profile, a Windows reinstall, or a copied `licence.json`) is `unlicensed` with the reason `binding-mismatch`, never a lapse, and the sign-in window says in plain words how to put the PC back. A token with no `bind` claim keeps working unchanged, and the next activation on that PC upgrades it. `unlicensed` (file missing, unreadable, unverifiable, minted for another PC, or bound to a proof this PC cannot reproduce) never takes the desktop away: `main.js` starts the shell anyway and opens the sign-in window (`electron/licenceStartup.js`). The one PC that meets setup instead is a packaged one with no genuine licence at all (missing, unreadable or unverifiable) on which Alpine never claimed the desktop: its Winlogon Shell is not Alpine and it has no `AlpineShell` Run entry (`setup.isDesktopClaimedByAlpine`). It has no Alpine desktop to lose, so it opens the setup window whatever `.setup-complete` says, and `ensureShellRegistration` writes the Shell and Run values at startup only with a valid licence or on a desktop Alpine has already claimed. The Run entry counts because a reinstall (the installer's `customInit` points the Shell at Explorer while it replaces the files) and "Revert until next sign-in" both leave Explorer in the Shell value and rely on that entry and the next start to take the shell back; only the permanent revert and uninstall delete it. There is no grace, no lapse and no hand-back to Explorer for a licence, and nothing may add one. The trust root is the baked key list only: never add a key cache under userData or an environment override that a release build honours. The same rule covers the marketplace signing key in `electron/pluginSignature.js`: a release build reads `electron/marketplacePublicKey.generated.js` (written by the same generator from `ALPINE_MARKETPLACE_PUBKEY`) and ignores the environment. A release build refuses, before downloading it, any marketplace bundle whose signature does not verify against that key (`electron/pluginMarketplace.js`), and both the generator and `release.yml` fail a release build that has no key. The marketplace base URL follows the same rule: a release build uses only the baked https base or the default in `electron/marketplaceConfig.js`. The updater is the one remaining call that carries the licence token: it sends `licence.currentToken()` as a bearer header to the licence-gated feed at `build.publish.url` about every six hours, skips checks without a token, and when the feed refuses the licence (refunded, released or revoked) it reports on the Updates page that updates are not available for this licence and touches nothing else. The Updates page has a Nightly builds switch that moves the updater between `latest.yml` and `nightly.yml` and a "What's new" row that opens the website's changelog; `RELEASING.md` covers the channels. `electron/modules/updater.js` still honours `checkForUpdates: false` in `<userData>/update-prefs.json` (the updater then makes no request at all, scheduled, by hand or after a sign-in), but settings no longer shows a switch for it. Every handler that changes the machine (registering the shell, the Run entry, test-out) must call `licence.requireValid()` in the main process before acting; the renderer is never the gate.

### Plugin API is a public contract
Published third-party plugins are built against `window.alpine` (`src/plugins/pluginRuntime.ts`), the backend `ctx` (`electron/pluginBackendContext.js`, which `electron/pluginBackendRuntime.js` hands to a plugin's `start`), the `plugin.json` fields `electron/pluginManifest.js` reads, and `@alpine/plugin-sdk`. Change them additively only: a new optional field, a new member, a new setting type behind `since`. Renaming or removing anything, or changing behaviour a plugin can observe, is a breaking change. It needs a new `PLUGIN_API_VERSION` (`packages/plugin-sdk/src/constants.ts`), the previous version stays in `SUPPORTED_API_VERSIONS` for at least one stable release, and the website docs (AlpineShell/website `src/app/docs/content/plugins/`) and the release notes change in the same release. `electron/pluginApiSurface.test.js` (the backend `ctx` and the `plugin.json` fields) and `src/plugins/pluginApiSurface.test.ts` (`window.alpine`) record what API version 1 plugins use and fail when any of it disappears: add to those lists when the API grows, never delete from them while the version is supported. `electron/pluginCompat.js` decides whether this app runs a plugin: an `apiVersion` above every supported one requires a newer Alpine, one below them was made for an older Alpine and waits for a plugin update, and an `engines.alpineShell` range that leaves this version out names the range. The store refuses an incompatible catalogue entry before downloading it and Browse shows it as not compatible; the community store build refuses an unsupported `apiVersion`.

## Commands

Run from the repo root; Bun resolves the right workspace via `--filter`.

- `bun start` (or `bun start app`) — Start the full desktop app (Vite dev server + Electron). Replaces `explorer.exe` with Alpine Shell while running.
- `bun run build` — Build the Windows installer (Vite build + electron-builder).
- `bun run release` — Build the installer and publish it to Railway/MinIO.

Building needs the Rust MSVC toolchain for the native add-on; `bun start` builds it too and falls back to the PowerShell helpers when it cannot.

Desktop-only iteration: `bun --filter alpine-shell dev` (Vite server only), `bun --filter alpine-shell electron` (Electron only; requires Vite already running).

## Code Conventions

- **No descriptive text in the UI by default.** A page title, a section heading or a control that is clear on its own gets no subtitle, description or helper paragraph under it. Add one only when someone would otherwise not know what a thing does or what is about to happen, and then keep it to one short sentence. Explaining how something works belongs in the docs, not on the screen where it sits: walls of grey text make the interface look worse, not clearer.
- **UI text is not selectable.** `src/index.css` sets `user-select: none` on `body`, so labels, headings and rows in every shell window (the Ridge, settings, setup, the desktop) cannot be selected, like a native settings app; inputs, textareas and editable content stay selectable. When a value is one someone will want to copy (an IP or MAC address, a version or build number, an error message, a path or id), add `select-text` to the element that shows it. Never turn selection back on for a whole page or card.
- **No code comments. None.** Name functions, variables, and types descriptively instead. This covers every kind: file headers, block comments explaining a design decision, `//` notes above a tricky line, and comments in tests. If a decision needs explaining, it belongs in the commit message or the pull request, where it is read once by a reviewer — not in the file, where it is read forever and rots. If a line needs explaining, rename something until it does not.
- **Single responsibility.** Each function does one thing.
- **DRY.** Use `useShellState` for read-only hooks. Use `runPowerShell` from `electron/powershell.js` for one-shot PowerShell commands.
- **No default exports** except for React components (React convention).
- **Type definitions** go in `src/types/shell.d.ts`, not inline in components or hooks.
- **File naming**: camelCase for all source files. Hook files are named after their exported function (e.g., `useMonitors.ts` exports `useMonitors`).
- **Never assert a Windows path literal in a test.** The shell is Windows-only but CI runs on Linux, where `C:\...` is a *relative* path — so `path.resolve` prepends the runner's working directory and the assertion fails only in CI, after passing locally. For an absolute fixture directory write `path.resolve(path.join(path.sep, 'plugins', 'com.example'))`, which is absolute on both platforms, and build expected values from that same constant. A `C:` literal is only safe for a value the code under test passes through without resolving.
- **Require `electron` inside the function that uses it**, never at module scope, in any `electron/` module that has a test. CI builds with `ELECTRON_SKIP_BINARY_DOWNLOAD`, so a module-scope `require('electron')` throws there and the test file fails to import before a single case runs. `shellNotice.js` and `pluginWindows.js` both learned this the same way.

## Key Technical Details

- **Topbar transparency**: The topbar window is transparent and uses main-process cursor tracking (not `{ forward: true }`) to toggle `setIgnoreMouseEvents`. This avoids click-through issues on Windows layered windows.
- **Native add-on**: the Rust add-on in `native/` (`alpine_native.node`, built by `scripts/buildNative.js` with napi-rs and the `windows` crate) hosts Core Audio (volume, devices, the microphone's capture sessions), Store app activation, the built-in panel's brightness over WMI, the media session (`GlobalSystemMediaTransportControlsSessionManager`) and the launcher's browser tab search. It also reads the precision touchpad's raw input on its own thread (`touchpad_watcher.rs`, a message-only window), assembles the contact frames there and wakes JS only for frames a three-finger swipe can use (`touchpad_frames.rs`), and `touchpadGestures.js` turns a three-finger sideways swipe into the Alt+Tab switcher, held open until the fingers lift. Each COM feature runs its COM calls in order on its own worker thread (`com_worker.rs`; audio, brightness, media and browser tabs MTA, activation STA), so the main process never waits on them and a slow app launch or a hung browser never delays a volume read. `appActivator.js` launches packaged AUMIDs through it and falls back to the PowerShell helper (`appActivatorPowerShell.js`) when it is missing; `ALPINE_APP_ACTIVATION_BACKEND=powershell` forces the helper in development. `browserTabs.js` lists and selects tabs through it (UI Automation for Chromium, MSAA for Firefox, each call bounded by a deadline) and falls back to `browserTabsPowerShell.js`; `ALPINE_BROWSER_TABS_BACKEND=powershell` forces the helper in development. `mediaSession.js` follows the playing media through the add-on's WinRT change events (`mediaSessionEvents.js`, re-read every five seconds in case an app raises none) and falls back to the old polling PowerShell helper (`mediaSessionPowerShell.js`, `electron/scripts/media.ps1`) when the add-on is missing; `ALPINE_MEDIA_BACKEND=powershell` forces it in development. Never block on a WinRT async operation on an STA thread.
- **Volume control**: `volume.js` talks to Core Audio through the add-on. `audioEndpoint.js` falls back to the old persistent PowerShell helper (`audioEndpointPowerShell.js`, `electron/scripts/audio.ps1`) when the add-on is missing, and `ALPINE_AUDIO_BACKEND=powershell` forces it in development. With the add-on, volume and mute changes are pushed by an `IAudioEndpointVolumeCallback` on the default output and device changes by the `IMMNotificationClient`, so `volume.js` polls only every 15 seconds as a safety net; with the PowerShell helper it polls every second. `microphone.js` lists the apps capturing audio through the add-on (`microphoneCapturersNative.js`) and falls back to the old helper (`microphoneCapturersPowerShell.js`, `electron/scripts/microphoneStatus.ps1`); `ALPINE_MICROPHONE_BACKEND=powershell` forces it in development. Never require the add-on at module scope in a tested module: CI runs on Linux and has no add-on.
- **Brightness**: External monitors use DDC/CI via dxva2.dll (koffi FFI). The built-in panel's brightness and every monitor's EDID identity come from `root\WMI` through the add-on (`wmi_brightness.rs`, on its own MTA worker thread), and a `WmiMonitorBrightnessEvent` subscription on a separate thread pushes Fn-key and Windows changes to `brightness.js` within a quarter second; the 15-second poll stays as the safety net. `brightnessWmi.js` falls back to the old PowerShell commands (`brightnessWmiPowerShell.js`, no push) when the add-on is missing, and `ALPINE_BRIGHTNESS_BACKEND=powershell` forces them in development. DDC/CI and WMI are both probed at startup.
- **Wi-Fi and Ethernet**: `electron/modules/network.js` reads everything natively through koffi, every five seconds (a minute under battery saver): the Wi-Fi link, radio and network list from `wlanapi.dll` (`networkNative.js`, `wifiNative.js`, all off the main thread with `.async`) and the wired link from `GetIfTable2`, where only a hardware Ethernet interface with a connector and media counts, so Hyper-V `vEthernet`, VPN and tunnel adapters never do. `NetworkStatus` describes the primary connection and always carries the Wi-Fi link in `wifi`, so Wi-Fi stays visible while Ethernet is up. Connecting is decided by the pure rules in `wifiOperations.js`: a saved profile is used as is, an open or OWE network gets a profile without asking, a WPA/WPA2/WPA3-Personal network asks for its password, Enterprise and WEP are refused (`wifiProfiles.js` builds the profile XML). The outcome comes from polling the interface state into `classifyAttempt`, never from the call being accepted, and a profile Alpine created for an attempt that failed is deleted, so a wrong password is never kept. Many laptops (HP LAN/WLAN Switching, Lenovo and Dell equivalents) switch the Wi-Fi radio off by themselves while Ethernet is connected, seconds after anyone turns it on; Alpine cannot stop that, so `WifiState` carries `ethernet` and `offForEthernet` (a system on→off of the radio Windows reported, not Alpine's held toggle, while Ethernet is up and nobody asked for off) and the surfaces say "Using Ethernet" or "Off while Ethernet is connected" instead of an empty list. On HP the firmware setting is read once at startup (`wifiSwitching.js`: the "LAN / WLAN Auto Switching" entry of `HP_BIOSEnumeration` plus the running HP switching service), and while it is on and Ethernet is connected (`blockedByEthernet`) the shell offers no Wi-Fi toggle and shows only that Ethernet is connected. The renderer reads one `WifiState` (`useWifi`) and runs every join through `useWifiJoin`. Only setting the radio still spawns PowerShell (`wifiRadio.ps1`); never parse `netsh` output, which is localized.
- **AppBar**: Reserves screen work area via `SystemParametersInfoW(SPI_SETWORKAREA)` so maximized windows don't overlap the topbar.
- **Keyboard shortcuts**: One low-level keyboard hook (`electron/modules/keyboardHook.js`) serves the whole shell. It lives on a thread of its own (`electron/keyboardHookWorker.js`, started by `keyboardHookThread.js`), because Windows holds every keystroke on the PC until the hook returns: the hook thread asks the main process about each key and waits at most `VERDICT_WAIT_MS` (150 ms, `keyboardHookPolicy.js`) for the answer through a `SharedArrayBuffer`. A key the main process has not answered by then goes through untouched, the main process skips it when it gets there (just as it never saw a key Windows timed out), and while it is still behind the hook thread lets keys through without waiting, so a stalled main process slows no one's typing. The main-thread hook is only the fallback when the hook thread will not start. `routeKeyboardInput` in `main.js` hands each key to an ordered chain, and the first handler that claims a key swallows it: the shortcut recorder (which owns every key while Keyboard shortcuts in settings waits for a new one), the Win tap that opens search, the emoji and display-mode captures (which own the keys while their picker is open), the shell shortcuts, the Alt+Tab switcher (`windowSwitcher.js`), then the fixed-surface guard (`fixedSurfaceKeys.js`), which swallows Windows' own Win+arrow, Win+Shift+arrow and Alt+F4 while a shell surface that nobody arranges (the Ridge with its launcher and menus, the desktop, the screenshot overlay) has focus, so Windows never moves, stretches, minimizes or closes it. Settings, plugin windows and setup stay arrangeable like any app. Every shell shortcut is one row in `SHORTCUT_BINDINGS` (`shellShortcutBindings.js`) plus a `shellHotkeys.on(action, …)` in `main.js` and a row in `src/settings/shortcutCatalogue.ts`, and a test fails when the two lists drift. The row holds the default keys; what someone sets on the Keyboard shortcuts page is stored in `<userData>/shell-shortcuts.json` and applied by `shellShortcuts.js`, which refuses keys without Win, Ctrl or Alt, keys Windows keeps (Alt+Tab, Alt+F4, Ctrl+Alt+Del, Win+L, Ctrl+Esc) and keys another shortcut has. Never install a second keyboard hook.
- **Other apps' windows**: the main process never waits on another app. A window that is busy answers nothing until it is done, and every call that sends it a message synchronously (`ShowWindow`, `SetWindowPos` without `SWP_ASYNCWINDOWPOS`, `BringWindowToTop`, `SetWindowPlacement`, `PrintWindow`, a `SendMessage` without a short timeout) stalls the whole shell for as long, which is what the `AppHangXProcB1` reports against Chrome, Modrinth, dwm.exe and Explorer were. Show and move another app's window with `ShowWindowAsync` and `SWP_ASYNCWINDOWPOS`, broadcast with `SendNotifyMessageW`, and leave a window `IsHungAppWindow` reports alone. Pixels come from `electron/modules/windowCapture.js`: the Alt+Tab thumbnails (`PrintWindow`) and the title-bar colour (a screen copy, which waits on dwm.exe) are drawn in a utility process (`windowCaptureProcess.js`) that is killed when one capture takes longer than two seconds, and a window that timed out is skipped for a minute. Tiling still restores a maximized window with a blocking `ShowWindow(SW_SHOWNOACTIVATE)`, because it measures the restored frame on the next line.
- **Desktops**: Windows' own virtual desktops live in Explorer, so Alpine keeps its own (`electron/modules/virtualDesktops.js`, pure rules in `virtualDesktopsPolicy.js`). A switch hides the switcher-eligible windows on screen with `ShowWindowAsync(SW_HIDE)` and shows the target desktop's with `SW_SHOWNA`; a window belongs to the desktop it was last seen on. Every hidden window is written to `<userData>/virtual-desktops-hidden.json`, `will-quit` shows them all again, and the next start shows any a crash left hidden, so a window can never be lost. Win+Ctrl+Left/Right switch, Win+Ctrl+Shift+Left/Right carry the focused window along, Win+Ctrl+D adds and Win+Ctrl+F4 closes a desktop.
- **Test out**: The setup window's test-out is the one place Alpine ends Explorer (`setup.beginTestSession`). It first starts a hidden helper (`revertScript.buildRestoreExplorerOnExitScript`) that waits for this Alpine process to exit and starts Explorer unless a shell window is back within ten seconds, then posts `WM_USER + 436` (the taskbar's "Exit Explorer") to Explorer's `Shell_TrayWnd`, waits for that process to end and only then starts shell mode, so `SetShellWindow` succeeds and tray icons re-register with Alpine. Nothing is written to the registry, so the next sign-in is Explorer again. During a test-out the Revert page offers only Return to Windows (`setup/end-test-session`, which starts Explorer as soon as Alpine has exited), and `setup.js` refuses the install reverts, because the temporary revert would write Alpine into the Shell value and the permanent one resets the cursors. Never force-kill Explorer instead: Winlogon respawns a shell it started when that shell is killed. A packaged start that claims the shell registration while Explorer holds the desktop (a sign-in after a reinstall or a revert until next sign-in, or a Start-menu launch, which also ends a revert until next sign-in) retires Explorer the same way before shell mode starts (`setup.claimDesktop`), without making the session a test-out.
- **Never beside Explorer**: a packaged Alpine never runs its shell while Explorer holds the desktop (`shellExclusivity.planShellStartup`). If Explorer will not leave, Alpine exits instead; a test-out that cannot retire Explorer is refused; a Start-menu launch after the permanent revert opens setup; a launch for an `alpine-shell://` link or a handled file exits when Alpine is not already running. While the shell runs, `setup.keepExplorerOffDesktop` checks every five seconds and retires an Explorer that takes the desktop, or shuts Alpine down if it stays. The only overlap allowed is the moment of an update hand-over.
- **SmartScreen prompt**: Windows draws "Windows protected your PC" by launching its own prompt app (`Microsoft.Windows.Apprep.ChxApp`) as a modal experience, and it asks Explorer's ImmersiveShell (`CLSID {C2F03A33-…}`) for the `IModalWindowExperienceManager` that hosts it. Without Explorer that class is not registered, so every launch of a downloaded file used to be cancelled silently (`ERROR_CANCELLED`), from Alpine, a browser or any other app. While Alpine acts as the shell, `smartScreenHost.js` runs `electron/scripts/smartScreenHost.cs` (compiled at runtime by the in-box C# 5 `csc`, so keep it ASCII), which registers itself as ImmersiveShell and answers only that one service: `ShowForContractWithPlugin` (vtable slot 8) for the ChxApp gets SmartScreen's own HTML and the marshalled `ProtocolForResultsOperation` from the serialized input buffer, and the helper reports `{ UserAction: 'run' | 'norun' }` back through it, so SmartScreen still makes every decision. Alpine shows the prompt on the topbar (`smartScreenPrompt.js`, `smartScreenPanel.tsx`), and Run anyway is greyed out unless SmartScreen's HTML offers it. Every other ImmersiveShell service and modal experience still fails as before. The helper talks over stdin and stdout and exits when Alpine's end of the pipe closes, which revokes the registration, so it never outlives the shell and must never run while Explorer holds the desktop. `SEE_MASK_FLAG_NO_UI` makes Windows cancel without asking for the prompt at all, so `shellExecute` sends a file with an internet zone mark (`Zone.Identifier`, `ZoneId` 3 or higher) to a worker of its own that allows the prompt.

## Adding a New System Module

1. Create `electron/modules/yourModule.js` with `handlers` and `start(broadcast)` exports
2. Register it in `electron/main.js`: add to the `ipc.register(...)` call
3. Add IPC channels to `electron/preload.js` under the appropriate namespace
4. Add types to `src/types/shell.d.ts`
5. Create a hook in `src/hooks/` using `useShellState` for read-only data
6. Use the hook in your component
